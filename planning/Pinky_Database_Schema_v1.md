# Pinky — Database Schema v1

**Status:** Design specification  
**Depends on:** `Pinky_Architecture_v1.md`, `Pinky_Domain_Model_and_State_Machines_v1.md`  
**Scope:** SQLite schema for Foundations → Event Subsystem → Task/Occurrence → Scheduler  
**Implementation boundary:** No Execution-specific schema is defined here.

---

# 1. Purpose

This document derives Pinky's persistent storage model from the canonical domain model.

The database must provide:

- durable Event history
- reliable Event publication through an Outbox
- durable Task definitions
- durable Occurrences
- durable Scheduler state
- durable Resource capacity
- durable Reservations
- durable consumer progress
- explainable Scheduler decisions
- crash recovery

The database is a **source of truth**, not merely a cache for in-memory runtime objects.

---

# 2. Database Technology

Phase 1 uses:

```text
SQLite
+
WAL mode
+
foreign keys
```

Recommended initialization:

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
```

Other operational pragmas should be selected deliberately during implementation and benchmarked rather than copied blindly.

---

# 3. Schema Overview

The initial logical schema is:

```text
EVENT PLANE
────────────────────────────────────

events
outbox
consumer_offsets


WORK PLANE
────────────────────────────────────

tasks
occurrences


SCHEDULER PLANE
────────────────────────────────────

scheduler_work
resources
reservations
scheduler_decisions
```

Relationship overview:

```text
events
  │
  ├────────────→ outbox
  │
  ├────────────→ occurrences.trigger_event_id
  │
  └── causation_id / correlation_id

tasks
  │
  └──→ occurrences
           │
           └──→ scheduler_work
                    │
                    └──→ reservations ←── resources

occurrences
  │
  └──→ scheduler_decisions
```

# 4. ID Strategy

Phase 1 should use generated opaque IDs rather than exposing database row IDs as domain identifiers.

Recommended:

```text
UUID
```

or UUID-compatible string/byte representation.

The important requirement is:

- globally unique enough for the local runtime
- immutable
- generated by Pinky
- safe to pass across subsystem boundaries

SQLite's internal integer `rowid` should not become the public identity of domain entities.

For performance-sensitive tables, the exact SQLite representation (`TEXT`, `BLOB`, etc.) should be decided before implementation.

---

# 5. Timestamp Strategy

Store timestamps in a consistent UTC representation.

Use separate fields where semantics differ.

For example:

```text
occurred_at
received_at
created_at
updated_at
runnable_at
deadline_at
```

Do not use one generic timestamp field for unrelated semantics.

The database should not attempt to infer local timezone semantics from timestamp values.

Timezone/schedule configuration belongs to the scheduling policy.

# 6. Table: events

## Purpose

Durable historical Event store.

## Proposed schema

```sql
CREATE TABLE events (
    event_id        TEXT PRIMARY KEY,
    event_type      TEXT NOT NULL,
    source          TEXT NOT NULL,
    occurred_at     TEXT NOT NULL,
    received_at     TEXT NOT NULL,
    payload         TEXT NOT NULL,
    causation_id    TEXT,
    correlation_id  TEXT,
    schema_version  INTEGER NOT NULL
);
```

## Semantics

### `event_id`

Unique immutable Event identifier.

### `event_type`

Canonical Event type.

Examples:

```text
USER_MESSAGE
TIMER_FIRED
FILE_CHANGED
TASK_CREATED
OCCURRENCE_ACTIVATED
EXECUTION_COMPLETED
```

The exact registry of event types belongs to the Event subsystem.

### `source`

Identifies the producing source.

Examples:

```text
user
filesystem
timer
pinky
external_service
```

### `occurred_at`

Source event time.

### `received_at`

Pinky acceptance time.

### `payload`

Serialized event payload.

JSON is the likely Phase 1 representation.

### `causation_id`

Optional immediate cause.

### `correlation_id`

Optional broader interaction/workflow correlation.

### `schema_version`

Version of the Event payload contract.

---

# 7. Event Indexes

Likely indexes:

```sql
CREATE INDEX idx_events_type_time
ON events(event_type, occurred_at);

CREATE INDEX idx_events_source_time
ON events(source, occurred_at);

CREATE INDEX idx_events_correlation
ON events(correlation_id);

CREATE INDEX idx_events_causation
ON events(causation_id);
```

Do not create every possible index automatically.

Indexes should correspond to actual query patterns.

The Event Store will eventually need a retention strategy, but retention/deletion policy is deliberately not finalized in v1.

---

# 8. Table: outbox

## Purpose

Guarantee that persisted Events can be discovered and published after a process crash.

## Proposed schema

```sql
CREATE TABLE outbox (
    outbox_id       TEXT PRIMARY KEY,
    event_id        TEXT NOT NULL,
    created_at      TEXT NOT NULL,
    published_at    TEXT,
    attempt_count   INTEGER NOT NULL DEFAULT 0,
    last_attempt_at TEXT,
    status          TEXT NOT NULL,

    FOREIGN KEY (event_id)
        REFERENCES events(event_id)
);
```

Suggested states:

```text
PENDING
PUBLISHED
FAILED
```

The exact retry semantics belong to the publisher implementation.

## Index

```sql
CREATE INDEX idx_outbox_pending
ON outbox(status, created_at);
```

Potential uniqueness:

```text
one outbox entry per Event
```

may be enforced if Phase 1 uses a single publisher stream.

If multiple delivery targets are introduced later, the model may evolve to:

```text
event
  ↓
delivery target
  ↓
outbox/delivery record
```

Do not add this complexity prematurely.

---

# 9. Table: consumer_offsets

## Purpose

Durably track Event consumer progress.

## Proposed schema

```sql
CREATE TABLE consumer_offsets (
    consumer_id             TEXT PRIMARY KEY,
    last_processed_event_id TEXT,
    updated_at              TEXT NOT NULL
);
```

The exact cursor semantics require care.

A simple Event ID cursor is only safe when the consumer's ordering model supports it.

If Events are later partitioned or processed under more complex ordering semantics, this table may need:

```text
partition
sequence
cursor
```

For Phase 1 single-process operation, the simple model is sufficient if the Event consumption contract defines ordering clearly.

---

# 10. Table: tasks

## Purpose

Persistent Task definitions.

## Proposed schema

```sql
CREATE TABLE tasks (
    task_id                 TEXT PRIMARY KEY,

    name                    TEXT NOT NULL,
    description             TEXT,
    goal                    TEXT NOT NULL,

    execution_mode          TEXT NOT NULL,

    base_priority           INTEGER NOT NULL,

    trigger_definition      TEXT NOT NULL,
    eligibility_policy      TEXT,
    concurrency_policy     TEXT,
    deadline_policy        TEXT,
    backpressure_policy    TEXT,
    resource_requirements   TEXT,
    authorization_policy   TEXT,

    lifecycle_state         TEXT NOT NULL,

    created_at              TEXT NOT NULL,
    updated_at              TEXT NOT NULL
);
```

Policy fields are likely JSON in Phase 1.

The schema should not turn every policy attribute into its own column unless the Scheduler needs to query it directly.

---

# 11. Task Constraints

The database should enforce basic state validity where practical.

For example, application/domain logic should restrict:

```text
DRAFT
ACTIVE
PAUSED
CANCELLED
COMPLETED
```

The database may additionally use:

```sql
CHECK (lifecycle_state IN (...))
```

if the state vocabulary is considered stable enough.

The exact choice between DB-level state checks and application-level transition validation should be finalized during implementation.

The important rule is that invalid transitions must not be silently accepted.

---

# 12. Task Indexes

Likely:

```sql
CREATE INDEX idx_tasks_state
ON tasks(lifecycle_state);

CREATE INDEX idx_tasks_execution_mode
ON tasks(execution_mode);

CREATE INDEX idx_tasks_priority
ON tasks(base_priority);
```

The priority index may not be useful if most scheduler queries operate through Occurrences rather than Tasks.

Do not retain an index merely because the column exists.

# 13. Table: occurrences

## Purpose

One activation of a Task.

## Proposed schema

```sql
CREATE TABLE occurrences (
    occurrence_id       TEXT PRIMARY KEY,

    task_id             TEXT NOT NULL,
    trigger_event_id    TEXT,

    created_at          TEXT NOT NULL,
    runnable_at         TEXT NOT NULL,
    deadline_at         TEXT,

    urgency             INTEGER NOT NULL DEFAULT 0,

    status              TEXT NOT NULL,

    coalesce_key        TEXT,
    metadata            TEXT,

    FOREIGN KEY (task_id)
        REFERENCES tasks(task_id),

    FOREIGN KEY (trigger_event_id)
        REFERENCES events(event_id)
);
```

---

# 14. Occurrence Semantics

An Occurrence belongs to exactly one Task.

```text
tasks.task_id
      ↓
occurrences.task_id
```

An Occurrence may have a triggering Event, but not every activation must necessarily have one.

For example:

```text
scheduled activation
```

may be generated by Pinky's temporal subsystem.

If every activation is eventually represented by an Event, `trigger_event_id` can become required. That should be decided based on the final Event semantics.

---

# 15. Occurrence Indexes

Likely scheduler-critical indexes:

```sql
CREATE INDEX idx_occurrences_task
ON occurrences(task_id);

CREATE INDEX idx_occurrences_status_runnable
ON occurrences(status, runnable_at);

CREATE INDEX idx_occurrences_deadline
ON occurrences(deadline_at);

CREATE INDEX idx_occurrences_coalesce
ON occurrences(task_id, coalesce_key);
```

The Scheduler will likely query by runnable time and state, making the second index particularly important.

---

# 16. Table: scheduler_work

## Purpose

Persist Scheduler operational state independently from Occurrence lifecycle.

## Proposed schema

```sql
CREATE TABLE scheduler_work (
    scheduler_work_id  TEXT PRIMARY KEY,

    occurrence_id      TEXT NOT NULL UNIQUE,

    state               TEXT NOT NULL,

    enqueued_at         TEXT,
    admitted_at         TEXT,
    dispatched_at       TEXT,

    last_evaluated_at   TEXT,

    priority_snapshot  INTEGER,

    FOREIGN KEY (occurrence_id)
        REFERENCES occurrences(occurrence_id)
);
```

The one-to-one relationship is:

```text
occurrence
    ↕
scheduler_work
```

---

# 17. Scheduler Work States

Conceptual values:

```text
WAITING
READY
QUEUED
ADMITTED
DISPATCHED
```

The exact persistence strategy may eventually avoid storing some derived states.

For example, `READY` may be derivable from:

```text
Occurrence activated
+
runnable_at <= now
+
not cancelled
+
not expired
```

However, retaining explicit scheduler state can simplify recovery and diagnostics.

The implementation should choose based on query complexity and correctness, not convenience alone.

---

# 18. Scheduler Work Indexes

Likely:

```sql
CREATE INDEX idx_scheduler_work_state
ON scheduler_work(state);

CREATE INDEX idx_scheduler_work_ready
ON scheduler_work(state, priority_snapshot);

CREATE INDEX idx_scheduler_work_occurrence
ON scheduler_work(occurrence_id);
```

If priority is recalculated dynamically rather than persisted, the scheduler may instead query Occurrence/Task fields directly.

The final index design should follow the actual candidate-selection SQL.

---

# 19. Table: resources

## Purpose

Represent finite scheduling capacity.

## Proposed schema

```sql
CREATE TABLE resources (
    resource_id       TEXT PRIMARY KEY,

    name              TEXT NOT NULL UNIQUE,
    resource_type     TEXT NOT NULL,

    capacity          INTEGER NOT NULL,

    state             TEXT NOT NULL,

    metadata          TEXT
);
```

Potential resource states:

```text
AVAILABLE
DISABLED
```

The exact state vocabulary can be expanded later.

---

# 20. Resource Capacity

The fundamental invariant is:

```text
0 <= reserved capacity <= total capacity
```

The database should not rely solely on a cached `available_capacity` value.

Preferred conceptual model:

```text
capacity
-
SUM(active reservations)
=
available capacity
```

If materialized availability is introduced for performance, it must be transactionally maintained.

For Phase 1, deriving availability from Reservations is easier to reason about.

---

# 21. Table: reservations

## Purpose

Record Scheduler-owned resource reservations.

## Proposed schema

```sql
CREATE TABLE reservations (
    reservation_id    TEXT PRIMARY KEY,

    resource_id       TEXT NOT NULL,
    occurrence_id     TEXT NOT NULL,

    quantity          INTEGER NOT NULL,

    created_at        TEXT NOT NULL,
    released_at       TEXT,

    status            TEXT NOT NULL,

    FOREIGN KEY (resource_id)
        REFERENCES resources(resource_id),

    FOREIGN KEY (occurrence_id)
        REFERENCES occurrences(occurrence_id)
);
```

Suggested states:

```text
ACTIVE
RELEASED
```

---

# 22. Reservation Indexes

```sql
CREATE INDEX idx_reservations_resource_status
ON reservations(resource_id, status);

CREATE INDEX idx_reservations_occurrence
ON reservations(occurrence_id);
```

Potential uniqueness constraints depend on whether one Occurrence may reserve the same Resource multiple times.

For Phase 1, it is simpler to make the Scheduler produce one reservation record per resource requirement per admission.

---

# 23. Resource Admission Transaction

This is one of the most important database operations in Pinky.

Conceptually:

```text
BEGIN IMMEDIATE

1. Read candidate
2. Verify Scheduler state
3. Verify concurrency constraints
4. Read resource capacity
5. Read active reservations
6. Verify capacity
7. Insert reservation(s)
8. Mark scheduler_work = ADMITTED
9. Record decision
10. COMMIT
```

No other admission operation should be able to interleave in a way that causes over-reservation.

The exact SQL should be designed and tested explicitly.

---

# 24. SQLite Concurrency Consideration

SQLite allows many readers but serializes writes.

Therefore Scheduler admission should use short write transactions.

Avoid:

```text
BEGIN
    call external service
    run expensive calculation
    wait for LLM
    COMMIT
```

Never hold a database write transaction across:

- LLM inference
- network calls
- tool execution
- arbitrary sleeps

The transaction should only cover the state transition that requires atomicity.

---

# 25. Table: scheduler_decisions

## Purpose

Persist explainable scheduling decisions.

## Proposed schema

```sql
CREATE TABLE scheduler_decisions (
    decision_id          TEXT PRIMARY KEY,

    occurrence_id        TEXT NOT NULL,

    decision_type        TEXT NOT NULL,

    created_at            TEXT NOT NULL,

    priority_snapshot    INTEGER,
    resource_snapshot    TEXT,

    selected              INTEGER NOT NULL,

    reason                TEXT,
    details               TEXT,

    FOREIGN KEY (occurrence_id)
        REFERENCES occurrences(occurrence_id)
);
```

SQLite booleans are normally represented using integers:

```text
0 = false
1 = true
```

---

# 26. Decision Record Semantics

Examples of `decision_type`:

```text
ELIGIBLE
DEFERRED
BLOCKED_RESOURCE
BLOCKED_CONCURRENCY
ADMITTED
EXPIRED
SKIPPED
CANCELLED
```

The exact vocabulary should be kept small.

Decision records are explanatory evidence.

They do not control Scheduler state.

---

# 27. Decision Indexes

```sql
CREATE INDEX idx_scheduler_decisions_occurrence
ON scheduler_decisions(occurrence_id, created_at);

CREATE INDEX idx_scheduler_decisions_time
ON scheduler_decisions(created_at);
```

Decision retention can be introduced later if logs become large.

# 28. Foreign-Key Graph

The expected graph is:

```text

   │
   ├──────────────→ outbox
   │
   └──────────────→ occurrences
                         │
tasks ───────────────────┘
   │
   └──────────────→ occurrences
                         │

                  scheduler_work

                         ▼

                     /         \
                    /           \
             resources       occurrences

occurrences
   │
   └──────────────→ scheduler_decisions
```

Foreign keys should be enabled.

# 29. Deletion Policy

Pinky should be conservative with deletion.

## Events

Do not delete casually.

Historical events may be needed for:

- replay
- debugging
- causality
- audit
- recovery

## Tasks

A Task should normally be state-transitioned to:

```text
CANCELLED
```

rather than deleted.

## Occurrences

Historical Occurrences may be retained.

## Scheduler Work

Can potentially be archived/removed after terminal lifecycle and retention requirements are satisfied.

## Reservations

Released reservations can eventually be compacted/archived.

## Decision Records

Can eventually have a retention policy.

Phase 1 should prioritize correctness over aggressive database cleanup.

---

# 30. Transaction Boundaries

Several operations require atomic transactions.

## Event acceptance

```text
BEGIN
    insert event
    insert outbox
COMMIT
```

## Occurrence activation

Where required:

```text
BEGIN
    validate Task
    create Occurrence
    create Scheduler Work
    COMMIT
```

## Scheduler admission

```text
BEGIN
    verify candidate
    verify capacity
    create reservation
    mark admitted
    record decision
COMMIT
```

## Reservation release

```text
BEGIN
    mark reservation released
    update scheduler state if appropriate
    record decision/event
COMMIT
```

The exact relationship between Event creation and state transitions should be finalized so domain changes and their corresponding Events cannot diverge.

---

# 31. Event + Domain State Atomicity

A particularly important design decision:

When Pinky changes important domain state, it should generally be possible to persist:

```text
state change
+
corresponding Event
+
Outbox entry
```

within the same transaction.

For example:

```text
Task activated

BEGIN
    UPDATE task
    INSERT task activation event
    INSERT outbox
COMMIT
```

This creates a strong invariant:

> If the durable state transition exists, its corresponding Event is also durably available for publication.

This should be used where event publication is semantically required.

# 32. Migration Strategy

Schema changes should be versioned.

Recommended:

```text
migrations/
    001_initial.sql
    002_...
    003_...
```

or an equivalent migration framework.

Never modify an existing production schema manually without recording the migration.

The database should expose a schema version.

---

# 33. Recommended Initial Database Layout

```text
pinky/
    data/
        pinky.db
```

SQLite will manage its WAL/SHM files beside the database.

Do not store:

- LLM model files
- execution artifacts
- arbitrary logs
- large binary files

inside SQLite by default.

Those should have dedicated storage strategies.

---

# 34. What Should NOT Be Stored Here

Do not prematurely put these into the Phase 1 schema:

```text
LLM conversation transcripts
model weights
prompt caches
tool execution logs
browser sessions
large files
audio
video
embeddings
vector indexes
```

These belong to later subsystems unless a concrete Phase 1 requirement appears.

A few choices remain intentionally open:

### A. ID representation

```text
UUID as TEXT
vs
UUID as BLOB
```

### B. Event payload representation

Likely:

```text
JSON TEXT
```

### C. Policy representation

Likely JSON initially.

### D. Explicit versus derived Scheduler states

Need to benchmark/query both approaches.

### E. Consumer cursor semantics

Need to define ordering precisely before finalizing `consumer_offsets`.

### F. Event retention

Not required for the first implementation.

### G. Reservation quantity

Integer capacity units are sufficient initially.

### H. Multiple resource requirements

Likely represented as multiple reservation rows.

These are implementation decisions, not architectural gaps.

# 36. Database Invariants

The database implementation must preserve:

```text
1. Every Occurrence references an existing Task.

2. Every Scheduler Work item references one Occurrence.

3. Every Reservation references an existing Resource and Occurrence.

4. Active reservation quantity cannot exceed Resource capacity.

5. Event IDs are unique.

6. Domain IDs are immutable.

7. An Event cannot disappear because a consumer processed it.

8. Outbox publication does not delete Event history.

9. Scheduler admission cannot occur without required capacity.

10. A released Reservation cannot consume active capacity.

11. Invalid lifecycle transitions cannot be silently persisted.

12. Crash recovery cannot create duplicate active reservations for the same logical admission.

13. Durable state transitions that require Events must commit their Event/outbox atomically.

14. Scheduler transactions remain short.

15. External work is never performed while holding a database write transaction.
```

---

# 37. Candidate Scheduler Query

The eventual Scheduler will need a query conceptually equivalent to:

```text
Find Occurrences where:

    Task is ACTIVE

    AND Occurrence is ACTIVATED

    AND runnable_at <= now

    AND not expired

    AND Scheduler Work is READY/QUEUED

Order candidates according to:

    effective priority
    +
    bounded aging
    +
    deadline pressure
```

Then admission performs resource/concurrency checks.

The exact SQL should be developed only after the final priority model is encoded.

---

# 38. Recovery Queries

Startup recovery will need to identify:

### Stale scheduler work

```text
ADMITTED
DISPATCHED
```

with no corresponding live downstream state.

### Active reservations

```text
status = ACTIVE
```

whose owning work is no longer valid.

### Pending outbox

```text
status = PENDING
```

or retryable failures.

### Unprocessed consumer events

Based on the consumer cursor.

Recovery should reconcile these records rather than simply deleting them.

---

# 39. Phase 1 Schema Boundary

The database schema ends at:

```text
Scheduler
    ↓
Dispatcher boundary
```

There is intentionally no:

```text
executions
execution_attempts
tool_calls
llm_sessions
worker_processes
```

yet.

Those should be designed after the Event → Task → Occurrence → Scheduler implementation has been validated.

# 40. Recommended Implementation Order

Implement the database in this order:

```text
1. migrations / schema version

2. events

3. outbox

4. consumer_offsets

5. tasks

6. occurrences

7. scheduler_work

8. resources

9. reservations

10. scheduler_decisions

11. indexes

12. transaction helpers

13. recovery queries
```

Then test database invariants independently before connecting the subsystems.
