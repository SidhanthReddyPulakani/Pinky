# Pinky Event Subsystem v1

This is the implementation specification I would use as the next canonical planning document.

The objective is deliberately narrow: **build a reliable local event ingestion and persistence pipeline without prematurely implementing Task activation, scheduling, execution, or LLM behavior.**

---

## 1. Purpose

The Event Subsystem is responsible for converting occurrences from heterogeneous sources into **durable, normalized Pinky Events**.

Its responsibilities are:

```text
Source
  ↓
Reader
  ↓
Event Intake
  ↓
Validation
  ↓
Normalization
  ↓
Deduplication
  ↓
Event Store
  ↓
Event Router
```

It is **not** responsible for:

* deciding whether a Task should execute
* creating SchedulerWork
* prioritizing Tasks
* resource admission
* execution
* LLM invocation
* deciding what an Event "means"

Those belong to later subsystems.

---

# 2. Core Design Principle

The Event subsystem treats an Event as a **historical fact**.

For example:

```text
"File X changed at 14:32:05"
"User submitted message Y at 14:33:10"
"Timer fired at 14:35:00"
"Application Z emitted notification N"
```

The Event subsystem records that something happened.

It does not decide what Pinky should do about it.

Therefore:

```text
Event ≠ Task
Event ≠ Execution
Event ≠ SchedulerWork
```

---

# 3. Event Lifecycle

The canonical lifecycle is:

```text
SOURCE
   │
   ▼
RECEIVED
   │
   ▼
VALIDATED
   │
   ▼
NORMALIZED
   │
   ▼
DEDUPLICATED
   │
   ▼
PERSISTED
   │
   ▼
ROUTED
```

However, these are **processing stages**, not necessarily durable Event states.

The Event itself should remain an immutable historical record once persisted.

That distinction matters.

We should not create a database state machine such as:

```text
RECEIVED → VALIDATED → PERSISTED
```

unless a concrete operational requirement later demands it.

Instead:

```text
incoming data
     ↓
processing pipeline
     ↓
immutable Event
```

---

# 4. Event Model

The canonical Event should contain:

```text
Event
├── event_id
├── event_type
├── source
├── source_event_id
├── dedupe_key
├── occurred_at
├── received_at
├── payload
└── schema_version
```

### `event_id`

Pinky's unique identifier for the Event.

Generated by Pinky rather than relying on the source.

It is immutable.

---

### `event_type`

A stable machine-readable type.

Examples:

```text
filesystem.file_created
filesystem.file_modified
filesystem.file_deleted

user.message
user.command

timer.fired

application.notification
application.state_changed
```

The exact taxonomy should evolve as readers are implemented.

The Event subsystem should not require every possible event type to be known ahead of time.

---

### `source`

Identifies the producing subsystem/source.

Examples:

```text
filesystem
user
timer
application
device
network
```

This is distinct from `event_type`.

For example:

```text
source:
filesystem

event_type:
filesystem.file_modified
```

---

### `source_event_id`

Optional source-provided identifier.

It identifies the Event according to the producing source.

Example:

```text
source = calendar
source_event_id = "google-calendar-12345"
```

Not every source can provide one.

Therefore:

```text
source_event_id = NULL
```

is valid.

---

### `dedupe_key`

Optional logical identifier used to prevent duplicate ingestion.

This is deliberately separate from `source_event_id`.

For example, a reader might receive:

```text
source_event_id = abc123
dedupe_key = calendar:abc123:update:5
```

The deduplication mechanism operates on the logical identity represented by `dedupe_key`.

The database schema's uniqueness rules remain authoritative.

---

### `occurred_at`

When the underlying event actually happened.

This may differ substantially from ingestion time.

For example:

```text
occurred_at = 14:00
received_at = 14:05
```

---

### `received_at`

When Pinky received the event.

This should be assigned by Pinky rather than trusting an external source.

---

### `payload`

Structured event-specific data.

Example:

```json
{
  "path": "/home/user/document.txt",
  "operation": "modified",
  "size": 18342
}
```

The Event envelope stays stable while payload schemas can evolve.

---

### `schema_version`

Version of the Event payload/envelope schema.

This allows future migration and interpretation of historical Events.

---

# 5. Immutability

Once an Event is persisted:

**the Event should be treated as immutable.**

We should not allow:

```text
Event A
 ↓
modify payload
 ↓
Event A'
```

If a source produces a later fact, it should normally produce another Event.

For example:

```text
file.modified
file.modified
file.deleted
```

rather than mutating the first Event.

This gives Pinky an actual historical record.

---

# 6. Event Intake

`EventIntake` is the primary entry point for incoming Events.

Conceptually:

```text
EventIntake.accept(incoming)
```

Its responsibility is to enforce the ingestion contract.

Pipeline:

```text
incoming
   ↓
validate
   ↓
normalize
   ↓
derive/check dedupe identity
   ↓
persist
   ↓
return ingestion result
```

---

# 7. Validation

Validation should happen before persistence.

Validate:

### Required fields

```text
event_type
source
occurred_at
payload
schema_version
```

`source_event_id` and `dedupe_key` remain optional.

### Type correctness

For example:

```text
occurred_at → valid datetime
payload → structured serializable data
schema_version → valid version
```

### Size limits

The Event subsystem should eventually enforce configurable limits on:

```text
payload size
event type length
source length
identifier length
```

This prevents one broken reader from filling the database with enormous payloads.

Exact limits can be configuration rather than hard-coded domain rules.

---

# 8. Normalization

Normalization converts source-specific representations into the canonical Event representation.

For example, different readers may produce:

```text
datetime formats
identifier formats
path representations
enum representations
```

The Intake layer should normalize them before persistence.

A Reader should therefore be relatively thin.

---

# 9. Deduplication

This is one of the most important parts.

The Event subsystem must tolerate the same source event being delivered more than once.

Example:

```text
Reader
   ↓
Event A
   ↓
network retry
   ↓
Event A again
```

Pinky must not accidentally create two historical Events when they represent the same source delivery.

The basic mechanism is:

```text
dedupe_key
     ↓
database uniqueness constraint
```

The application can perform a preliminary lookup, but **the database constraint is the final authority**.

This protects against:

```text
Reader A ──┐
           ├── concurrent insertion
Reader B ──┘
```

where both check "doesn't exist" before attempting insertion.

---

# 10. Duplicate Result

Duplicate ingestion should not normally be treated as a system failure.

The Intake API should distinguish:

```text
ACCEPTED
DUPLICATE
REJECTED
```

Conceptually:

```python
result = await intake.accept(event)
```

could produce:

```text
Accepted(event_id)
Duplicate(existing_event_id)
Rejected(reason)
```

This makes duplicate handling explicit to readers.

---

# 11. Event Store

The Event Store provides durable persistence.

Conceptually:

```text
EventStore
├── append()
├── get()
├── exists()
└── query()
```

The actual implementation will use the persistence layer.

The Event subsystem should not issue SQL directly.

Architecture:

```text
EventIntake
     ↓
EventStore interface
     ↓
EventRepository
     ↓
SQLAlchemy
     ↓
SQLite
```

---

# 12. Event Queries

The initial Event Store should support enough querying for the rest of Pinky without becoming a generic query engine.

At minimum:

```text
get(event_id)

find_by_dedupe_key(dedupe_key)

find_by_source_event_id(source, source_event_id)

list_by_source(source)

list_by_type(event_type)

list_by_time_range(start, end)
```

Pagination should be supported for potentially large histories.

---

# 13. Event Router

After successful persistence:

```text
Event
 ↓
EventRouter
```

The Router determines which registered consumers should receive the Event.

Conceptually:

```text
EventRouter
     │
     ├── Task trigger subsystem
     ├── audit/observability
     └── other future consumers
```

However, **routing must not determine whether something executes.**

For example:

```text
Event
 ↓
Task trigger matches
 ↓
Occurrence
```

The Router may facilitate that handoff, but Task activation remains the responsibility of the Task subsystem.

---

# 14. Routing Guarantees

Phase 1 should initially use **in-process delivery**.

We don't need Kafka, RabbitMQ, Redis Streams, NATS, etc.

The flow is:

```text
persist Event
     ↓
publish to in-process consumers
```

Persistence comes first.

Therefore:

```text
Event Store
     ↓
success
     ↓
Router
```

not:

```text
Router
 ↓
Event Store
```

This prevents consumers from acting on an Event that wasn't successfully recorded.

---

# 15. What Happens If Routing Fails?

This is an important distinction.

Suppose:

```text
Event persisted
     ↓
Router
     ↓
consumer crashes
```

The Event **must not disappear**.

The Event is already durable.

This is why the Event Store is authoritative for historical Events.

However, if we require guaranteed delivery to downstream consumers, we eventually need an outbox/delivery mechanism.

For Phase 1, we should therefore distinguish:

### Event persistence guarantee

**Required.**

### Consumer delivery guarantee

**To be explicitly implemented when the consumer contract requires it.**

We shouldn't pretend in-process routing is durable messaging.

---

# 16. Reader Contract

Readers are producers.

A Reader should conceptually implement:

```python
class EventReader(Protocol):
    async def start(self) -> None:
        ...

    async def stop(self) -> None:
        ...
```

The Reader's internal behavior is source-specific.

But its output boundary is always:

```text
Reader
  ↓
EventIntake.accept()
```

---

# 17. Reader Responsibilities

A Reader owns:

* connecting to its source
* listening/polling
* source-specific parsing
* detecting source events
* constructing candidate Events
* submitting them to Intake
* maintaining source-specific cursors/checkpoints where necessary

A Reader does **not** own:

* SQLite
* deduplication policy
* Task activation
* Scheduler
* Execution
* LLM invocation

---

# 18. Listener vs Polling

The Event subsystem must support both.

### Listener

For example:

```text
OS notification
      ↓
Reader callback
      ↓
Event
```

### Polling

For example:

```text
periodic poll
      ↓
source query
      ↓
detect changes
      ↓
Event
```

The Event subsystem doesn't care which mechanism produced the Event.

That's an implementation detail of the Reader.

---

# 19. Reader Reliability

Readers must be designed around failure.

A source may:

```text
disconnect
timeout
crash
return malformed data
return duplicates
stop responding
```

The Reader should not bring down the Core.

Conceptually:

```text
Reader failure
     ↓
Reader supervisor
     ↓
restart/backoff
```

The Reader supervisor is arguably part of the Runtime subsystem rather than the Event domain itself.

We can implement the simplest version first.

---

# 20. Backpressure

This matters because Readers can produce Events faster than the Core can persist them.

For example:

```text
Filesystem Reader
       │
       │ 10,000 events/sec
       ▼
    Intake
       │
       │ 2,000/sec
       ▼
   Event Store
```

Therefore, Intake should eventually have a bounded asynchronous ingestion queue.

Conceptually:

```text
Reader
  ↓
bounded queue
  ↓
Intake workers
  ↓
Event Store
```

But **we shouldn't introduce a complex queueing system in the first implementation**.

Start with direct asynchronous Intake.

Then benchmark.

If backpressure becomes necessary:

```text
bounded asyncio.Queue
```

is sufficient for Phase 1.

---

# 21. Concurrency

Multiple Readers may operate simultaneously:

```text
Filesystem ──┐
Timer ────────┤
Application ──┼──→ Intake
Network ──────┤
User ─────────┘
```

Therefore Intake must be safe when multiple events are being processed concurrently.

SQLite remains the durable serialization boundary.

We should avoid introducing a global Python lock around all Event ingestion unless measurements demonstrate that one is necessary.

---

# 22. Transaction Boundary

The fundamental transaction is:

```text
validate
   ↓
normalize
   ↓
persist Event
```

This should be atomic from the Event Store's perspective.

If persistence fails:

```text
Event
 ↓
DB failure
 ↓
NOT ACCEPTED
```

The caller should not receive `ACCEPTED`.

---

# 23. Failure Semantics

We should distinguish:

### Invalid Event

```text
REJECTED
```

No persistence.

### Duplicate Event

```text
DUPLICATE
```

No new Event created.

### Temporary persistence failure

```text
ERROR
```

Reader may retry according to its retry policy.

### Permanent database failure

Core/runtime health should reflect the failure.

---

# 24. Event IDs vs Deduplication

These must never be confused.

```text
event_id
```

answers:

> What is this Event inside Pinky?

Whereas:

```text
dedupe_key
```

answers:

> Is this incoming delivery already represented by an Event?

Therefore:

```text
event_id ≠ dedupe_key
```

Even if a source's identifier happens to be used in constructing a dedupe key.

---

# 25. Persistence vs Replay

Because Events are historical facts, the Event Store naturally becomes a replay source.

For example:

```text
SQLite
  ↓
historical Events
  ↓
replay
  ↓
Event Router
```

This will eventually be useful for:

* debugging
* rebuilding derived state
* testing
* recovery
* auditing

But **replay should not be implemented as part of the first ingestion milestone**.

We should first ensure that persistence semantics are correct.

---

# 26. Initial Event Subsystem API

The first implementation should probably expose only a small internal API:

```text
EventIntake
├── accept(event)
│
EventStore
├── append(event)
├── get(event_id)
├── find_by_dedupe_key(key)
└── query(...)
│
EventRouter
├── register(...)
├── unregister(...)
└── publish(event)
│
EventReader
├── start()
└── stop()
```

Don't over-abstract it beyond this initially.

---

# 27. Testing Strategy

Testing should be extensive here because the Event subsystem becomes foundational infrastructure.

### Unit tests

Test:

```text
Event validation
Event normalization
ID generation
dedupe behavior
serialization
deserialization
routing
```

### Persistence tests

Test:

```text
insert
retrieve
duplicate constraint
transactions
rollback
restart
query
```

### Integration tests

At minimum:

```text
Reader
  ↓
Intake
  ↓
Store
  ↓
Router
```

### Failure tests

Simulate:

```text
malformed Event
duplicate Event
database unavailable
database constraint violation
consumer exception
reader exception
```

---

# 28. First Concrete Reader

Don't start with filesystem monitoring.

Create:

```text
SyntheticEventReader
```

Its purpose is testing.

For example:

```text
SyntheticEventReader
      ↓
EventIntake
      ↓
SQLite
      ↓
Router
```

It can generate deterministic Events on demand.

Once this works, we can implement a real Reader.

---

# 29. First Real Reader

I'd then choose a relatively isolated OS-level source.

A filesystem reader is a good candidate because it exercises:

```text
external source
listener
source-specific metadata
duplicates
bursts
backpressure
```

That will expose many of the reliability problems that a trivial timer reader won't.

---

# 30. Phase 1 Boundary

The completed Event subsystem should look like:

```text
                 ┌──────────────────┐
                 │     Readers      │
                 └────────┬─────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │   Event Intake   │
                 │                  │
                 │ Validate         │
                 │ Normalize       │
                 │ Deduplicate     │
                 └────────┬─────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │    Event Store   │
                 │                  │
                 │    SQLite        │
                 └────────┬─────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │   Event Router   │
                 └────────┬─────────┘
                          │
                          ▼
                    Task Subsystem
```

The Task subsystem is the **next consumer**, not part of the Event subsystem.

# Implementation Order

Now that the specification is defined, I would implement exactly this:

```text
1. Event domain model
        ↓
2. Event validation
        ↓
3. Event serialization
        ↓
4. Event repository interface
        ↓
5. SQLAlchemy Event persistence
        ↓
6. EventIntake
        ↓
7. Deduplication
        ↓
8. EventRouter
        ↓
9. EventReader protocol
        ↓
10. SyntheticEventReader
        ↓
11. Integration tests
        ↓
12. Real first Reader
```

And importantly, **we should not implement Task activation yet**.

Once steps 1–11 pass, we'll have something much more valuable than a collection of classes: we'll have a verified **Event → durable Event → routed Event pipeline** that the Task subsystem can safely consume.

If you want to keep the repository documentation clean, save the above as:

```text
planning/Pinky_Event_Subsystem_v1.md
```

Then we're ready to move from planning into the **actual Python implementation**, starting with the project skeleton and Event domain model.
