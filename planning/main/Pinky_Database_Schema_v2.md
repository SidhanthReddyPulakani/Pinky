# Pinky — Database Schema v2

**Status:** Canonical Phase 1 database specification  
**Supersedes:** `Pinky_Database_Schema_v1.md`  
**Depends on:** `Pinky_Architecture_v1.md`, `Pinky_Domain_Model_and_State_Machines_v1.md`  
**Scope:** Foundations → Event Subsystem → Task/Occurrence → Scheduler  
**Implementation boundary:** No Execution-specific domain schema is defined here.

---

# 1. Purpose

This document defines Pinky's authoritative Phase 1 persistence model.

The database must support:

- durable Event history
- reliable Event publication
- durable Event replay
- durable consumer progress
- persistent Task definitions
- multiple Task triggers
- Task dependencies
- persistent Occurrences
- persistent Scheduler state
- persistent scheduling metadata
- resource capacity
- atomic resource Reservations
- explainable Scheduler decisions
- crash recovery

The database is a **source of truth for durable operational state**.

It is not merely a cache for in-memory runtime objects.

---

The domain model contains:

```text

Occurrence

```

The persistence model is:

```text
EVENT PLANE
────────────────────────────────────────

events

────────────────────────────────────────

task_triggers
task_dependencies
occurrences


SCHEDULER PLANE
────────────────────────────────────────

scheduler_work

reservations

```

Execution-specific tables are intentionally excluded.

# 3. Important v2 Corrections

Version 2 changes several important assumptions from v1.

## 3.1 Event log position is separate from Event identity

An opaque `event_id` is the domain identity.

A separate monotonically increasing `event_seq` is the durable log position used for consumer replay.

These are different concepts:

```text
event_id
    = identity of the Event

event_seq
    = position of the Event in Pinky's durable local event log
```

`event_seq` does **not** claim that the Event is semantically earlier than another Event. It only provides a stable persistence/replay cursor.

## 3.2 Event deduplication is persisted

Because Event Intake performs deduplication, the database must retain enough information to make deduplication durable.

v2 adds:

```text
source_event_id
dedupe_key
```

with source-scoped uniqueness where supplied.

## 3.3 Task triggers become a normalized persistence structure

A Task can have multiple trigger conditions.

Instead of placing all trigger definitions in one opaque Task field, v2 introduces:

```text
task_triggers
```

This is a persistence decomposition of the Task's trigger policy, not a new high-level domain concept.

It allows the Event/Trigger subsystem to efficiently locate Tasks affected by:

```text
EVENT
SCHEDULE
CONDITION
MANUAL
```

triggers.

## 3.4 Task dependencies become a relational structure

Dependencies are part of Task behavior, but the scheduler/trigger subsystem needs reverse lookup:

```text
Which Tasks depend on Task A?
```

v2 therefore introduces:

```text
task_dependencies
```

This is a persistence representation of the existing Task dependency concept.

## 3.5 Scheduler `QUEUED` is not a durable state

In-memory queue membership is derived operational state.

The database persists:

```text
WAITING
READY
ADMITTED
DISPATCHED
CANCELLED
EXPIRED
```

`ready_at` preserves when the work became ready without permanently mirroring an in-memory queue.

## 3.6 Reservations belong to SchedulerWork

A Reservation is created because SchedulerWork was admitted.

Therefore reservations reference:

```text
scheduler_work_id
```

rather than only an Occurrence.

## 3.7 Effective priority is diagnostic, not authoritative

SchedulerWork does not persist an authoritative current priority.

The Scheduler derives effective priority from current policy inputs.

Decision records capture the snapshot used for a particular scheduling decision.

# 4. Database Technology Assumptions

Phase 1 uses:

```text
SQLite
+
WAL mode
+
foreign keys
```

Recommended initialization:

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
```

Other operational settings should be selected deliberately during implementation.

---

# 5. ID Strategy

Domain entities use generated opaque identifiers.

Recommended initial representation:

```text
UUID-compatible TEXT
```

The exact UUID format can be standardized during implementation.

Rules:

- IDs are generated by Pinky.
- IDs are immutable.
- IDs are not reused.
- SQLite row IDs are not exposed as domain IDs.

The Event log sequence is an exception:

```text
event_seq INTEGER PRIMARY KEY AUTOINCREMENT
```

`event_seq` is an internal persistence cursor, not a domain identity.

---

# 6. Timestamp Strategy

Store timestamps in a single UTC representation.

Recommended:

```text
ISO 8601 UTC TEXT
```

Examples:

```text
occurred_at
received_at
created_at
updated_at
activated_at
runnable_at
deadline_at
ready_at
admitted_at
dispatched_at
released_at
finished_at
```

Do not collapse unrelated timestamp semantics into one field.

Schedule timezone semantics belong to the schedule trigger.

# 7. Table: events

## 7.1 Purpose

Durable historical Event log.

## 7.2 Schema

```sql
CREATE TABLE events (
    event_seq         INTEGER PRIMARY KEY AUTOINCREMENT,

    event_id          TEXT NOT NULL UNIQUE,

    event_type        TEXT NOT NULL,
    source            TEXT NOT NULL,

    occurred_at       TEXT NOT NULL,
    received_at       TEXT NOT NULL,

    payload           TEXT NOT NULL,
    metadata          TEXT NOT NULL DEFAULT '{}',

    causation_id      TEXT,
    correlation_id    TEXT,

    source_event_id   TEXT,
    dedupe_key        TEXT,

    schema_version    INTEGER NOT NULL
);
```

## 7.3 Semantics

### `event_seq`

Internal durable log position for replay.

It is not semantic or causal ordering.

### `event_id`

Canonical Pinky Event identity.

### `event_type`

Stable machine-readable Event type.

### `source`

Producing source or subsystem.

### `occurred_at`

When the source says the Event occurred.

### `received_at`

When Pinky accepted/persisted the Event.

### `payload`

Event-specific semantic data.

### `metadata`

Non-semantic metadata.

### `causation_id`

Immediate causal predecessor where known.

### `correlation_id`

Broader interaction/workflow correlation.

### `source_event_id`

Stable identifier supplied by the source when available.

### `dedupe_key`

Source/integration-specific deduplication identity when `source_event_id` is unavailable or insufficient.

### `schema_version`

Version of the event/payload contract.

# 8. Event Deduplication Constraints

Recommended durable uniqueness guards:

```sql
CREATE UNIQUE INDEX uq_events_source_event
ON events(source, source_event_id)
WHERE source_event_id IS NOT NULL;

CREATE UNIQUE INDEX uq_events_source_dedupe
ON events(source, dedupe_key)
WHERE dedupe_key IS NOT NULL;
```

Event Intake decides whether an incoming candidate is a duplicate.

The database provides the final uniqueness guard.

A duplicate candidate must not create a second logical Event.

# 10. Table: outbox

## 10.1 Purpose

Persist the fact that a stored Event still needs publication to the internal delivery layer.

The Outbox is not the Event Store and does not replace consumer progress.

## 10.2 Schema

```sql
CREATE TABLE outbox (
    outbox_id          TEXT PRIMARY KEY,

    event_id           TEXT NOT NULL UNIQUE,

    created_at         TEXT NOT NULL,

    status             TEXT NOT NULL
                       CHECK (status IN ('PENDING', 'PUBLISHED')),

    attempt_count      INTEGER NOT NULL DEFAULT 0
                       CHECK (attempt_count >= 0),

    last_attempt_at    TEXT,
    next_attempt_at    TEXT,

    published_at       TEXT,
    last_error         TEXT,

    FOREIGN KEY (event_id)
        REFERENCES events(event_id)
);
```

## 10.3 Semantics

A transient publication failure leaves the record:

```text
PENDING
```

and updates retry metadata.

`PUBLISHED` means the Event has been successfully handed to the durable internal delivery mechanism represented by the Outbox publisher.

Consumer completion is tracked separately by `consumer_offsets`.

---

# 11. Outbox Index

```sql
CREATE INDEX idx_outbox_pending

```

# 12. Table: consumer_offsets

## 12.1 Purpose

Track durable Event-consumer progress.

## 12.2 Schema

```sql
CREATE TABLE consumer_offsets (
    consumer_id              TEXT PRIMARY KEY,

    last_processed_event_seq INTEGER NOT NULL DEFAULT 0
                              CHECK (last_processed_event_seq >= 0),

    updated_at               TEXT NOT NULL
);
```

`0` means:

```text
before the first Event
```

The offset is a replay cursor, not semantic Event ordering.

---

# 13. Consumer Processing Rule

A durable consumer follows:

```text
read Event
    ↓
process Event
    ↓
persist consumer-owned state
    ↓
advance consumer offset
```

Where possible, the state change and offset update are committed in the same transaction.

If a crash occurs before the offset commit:

```text
Event may be processed again
```

Therefore consumer handling must be replay-safe.

# 14. Table: tasks

## 14.1 Purpose

Persistent Task responsibility and policy.

## 14.2 Schema

```sql
CREATE TABLE tasks (
    task_id                TEXT PRIMARY KEY,

    name                   TEXT NOT NULL,
    description            TEXT,
    goal                   TEXT NOT NULL,

    created_by             TEXT NOT NULL,

    execution_mode         TEXT NOT NULL
                           CHECK (
                               execution_mode IN (
                                   'DETERMINISTIC',
                                   'INTERACTIVE',
                                   'AUTONOMOUS'
                               )
                           ),

    base_priority          INTEGER NOT NULL,

    eligibility_policy     TEXT NOT NULL DEFAULT '{}',
    concurrency_policy     TEXT NOT NULL DEFAULT '{}',
    deadline_policy        TEXT NOT NULL DEFAULT '{}',
    backpressure_policy    TEXT NOT NULL DEFAULT '{}',

    resource_requirements  TEXT NOT NULL DEFAULT '{}',
    authorization_policy  TEXT NOT NULL DEFAULT '{}',

    constraints            TEXT NOT NULL DEFAULT '{}',

    input_spec             TEXT NOT NULL DEFAULT '{}',
    output_spec            TEXT NOT NULL DEFAULT '{}',

    metadata               TEXT NOT NULL DEFAULT '{}',

    lifecycle_state        TEXT NOT NULL
                           CHECK (
                               lifecycle_state IN (
                                   'DRAFT',
                                   'ACTIVE',
                                   'PAUSED',
                                   'CANCELLED',
                                   'COMPLETED'
                               )
                           ),

    created_at              TEXT NOT NULL,
    updated_at              TEXT NOT NULL
);
```

## 14.3 Design choice

Task trigger definitions and dependencies are not duplicated in `tasks`.

They are represented by:

```text
task_triggers
task_dependencies
```

This makes the database align with the architecture's support for multiple triggers and dependency lookup.

# 16. Table: task_triggers

## 16.1 Purpose

Relational persistence of Task trigger definitions.

A Task may have multiple triggers.

## 16.2 Schema

```sql
CREATE TABLE task_triggers (
    trigger_id          TEXT PRIMARY KEY,

    task_id             TEXT NOT NULL,

    trigger_type        TEXT NOT NULL
                        CHECK (
                            trigger_type IN (
                                'SCHEDULE',
                                'EVENT',
                                'CONDITION',
                                'MANUAL'
                            )
                        ),

    event_type          TEXT,

    spec_json           TEXT NOT NULL DEFAULT '{}',

    timezone            TEXT,

    enabled             INTEGER NOT NULL DEFAULT 1
                        CHECK (enabled IN (0, 1)),

    next_fire_at        TEXT,
    last_fired_at       TEXT,

    misfire_policy      TEXT,

    created_at          TEXT NOT NULL,
    updated_at          TEXT NOT NULL,

    FOREIGN KEY (task_id)
        REFERENCES tasks(task_id),

    CHECK (
        (trigger_type = 'EVENT' AND event_type IS NOT NULL)
        OR
        (trigger_type <> 'EVENT')
    )
);
```

`next_fire_at` is required logically for enabled schedule triggers, but it is better validated by Task/Trigger logic during activation than made a hard DB constraint if trigger creation can occur before its first schedule calculation.

## 16.3 Trigger types

### SCHEDULE

Time-based activation.

`spec_json` contains recurrence details.

`timezone` defines calendar semantics.

`next_fire_at` is Pinky's durable next wake point.

### EVENT

Triggered by a matching persisted Event.

`event_type` is the primary routing key.

`spec_json` contains optional event filters.

### CONDITION

Activated when a defined condition becomes true.

The observation mechanism is outside this schema.

### MANUAL

Activated explicitly.

Pinky owns:

```text
schedule semantics
next_fire_at
last_fired_at
misfire policy
```


# 19. Table: task_dependencies

## 19.1 Purpose

Persist Task-to-Task dependency relationships.

Phase 1 dependency semantics are intentionally minimal.

A dependency is satisfied when the referenced Task reaches:

```text
COMPLETED
```

## 19.2 Schema

```sql
CREATE TABLE task_dependencies (
    task_id             TEXT NOT NULL,

    depends_on_task_id  TEXT NOT NULL,

    condition           TEXT NOT NULL DEFAULT 'COMPLETED'
                        CHECK (condition = 'COMPLETED'),

    created_at          TEXT NOT NULL,

    PRIMARY KEY (task_id, depends_on_task_id),

    FOREIGN KEY (task_id)
        REFERENCES tasks(task_id),

    FOREIGN KEY (depends_on_task_id)
        REFERENCES tasks(task_id),

    CHECK (task_id <> depends_on_task_id)
);
```

---

# 20. Dependency Index

```sql
CREATE INDEX idx_task_dependencies_dependency
ON task_dependencies(depends_on_task_id);
```

This lets the runtime efficiently find:

```text
Tasks depending on Task A
```

when A completes.

---

# 21. Dependency Semantics

A dependency is an **eligibility condition**, not a trigger category.

Therefore `DEPENDENCY` is intentionally not a `task_triggers.trigger_type`.

Conceptually:

```text
Trigger:
    "when schedule/event/manual condition activates this Task"

Dependency:
    "whether that activated work is logically allowed to proceed"
```

This keeps trigger and eligibility semantics distinct.

# 22. Table: occurrences

## 22.1 Purpose

One activation of a Task.

## 22.2 Schema

```sql
CREATE TABLE occurrences (
    occurrence_id       TEXT PRIMARY KEY,

    task_id             TEXT NOT NULL,
    trigger_id          TEXT,

    trigger_event_id    TEXT,

    activation_key      TEXT NOT NULL UNIQUE,

    created_at           TEXT NOT NULL,
    activated_at         TEXT NOT NULL,

    runnable_at          TEXT NOT NULL,
    deadline_at          TEXT,

    urgency              INTEGER NOT NULL DEFAULT 0,

    status               TEXT NOT NULL
                         CHECK (
                             status IN (
                                 'PENDING',
                                 'ACTIVATED',
                                 'COMPLETED',
                                 'SKIPPED',
                                 'CANCELLED',
                                 'EXPIRED'
                             )
                         ),

    coalesce_key         TEXT,

    metadata             TEXT NOT NULL DEFAULT '{}',

    updated_at           TEXT NOT NULL,
    finished_at          TEXT,

    FOREIGN KEY (task_id)
        REFERENCES tasks(task_id),

    FOREIGN KEY (trigger_id)
        REFERENCES task_triggers(trigger_id),

    FOREIGN KEY (trigger_event_id)
        REFERENCES events(event_id)
);
```

# 23. Occurrence Activation Identity

`activation_key` is a durable logical idempotency key for activation.

Examples:

## Event trigger

```text
hash(trigger_id, event_seq)
```

## Scheduled trigger

```text
hash(trigger_id, scheduled_for)
```

## Manual activation

```text
hash(trigger_id, request_id)
```

The Trigger Engine determines the exact encoding.

The requirement is:

> Reprocessing the same logical trigger produces the same activation key.

The database uniqueness constraint then prevents duplicate Occurrences.

---

# 24. Occurrence Lifecycle

```text
PENDING
   ↓
ACTIVATED
   │
   ├──→ COMPLETED
   ├──→ SKIPPED
   ├──→ CANCELLED
   └──→ EXPIRED
```

`PENDING` can be transient and may be created/activated inside one transaction.

An Occurrence's lifecycle does not describe Scheduler queue membership.

# 26. Table: scheduler_work

## 26.1 Purpose

Persist Scheduler-owned state independently from the Occurrence lifecycle.

## 26.2 Schema

```sql
CREATE TABLE scheduler_work (
    scheduler_work_id   TEXT PRIMARY KEY,

    occurrence_id       TEXT NOT NULL UNIQUE,

    state               TEXT NOT NULL
                        CHECK (
                            state IN (
                                'WAITING',
                                'READY',
                                'ADMITTED',
                                'DISPATCHED',
                                'CANCELLED',
                                'EXPIRED'
                            )
                        ),

    ready_at             TEXT,
    admitted_at          TEXT,
    dispatched_at        TEXT,

    last_evaluated_at    TEXT,

    blocked_reason       TEXT,

    FOREIGN KEY (occurrence_id)
        REFERENCES occurrences(occurrence_id)
);
```

---

# 27. SchedulerWork State Semantics

### WAITING

Not currently runnable.

Examples:

```text
runnable_at is in future
dependency unresolved
condition unresolved
```

### READY

Eligible and runnable.

The in-memory run queue is built from READY work.

### ADMITTED

Resources/concurrency have been successfully reserved and the Scheduler has committed the work for dispatch.

### DISPATCHED

The work has been handed to the Dispatcher.

It does not mean execution succeeded.

### CANCELLED

Scheduler-side work cancelled before downstream completion.

### EXPIRED

Work can no longer be admitted because its validity/deadline has passed.

---

# 28. Why `QUEUED` Is Not Persisted

The architecture distinguishes:

```text
READY
QUEUED
```

conceptually.

But the database should persist authoritative operational state, not every detail of an in-memory data structure.

For Phase 1:

```text
READY = schedulable work
in-memory queue = implementation detail
```

The queue can be reconstructed after a crash from persistent READY work.

# 30. Priority Persistence Model

The Scheduler derives:

```text
base_priority
    ← Task

urgency
    ← Occurrence

deadline
    ← Occurrence

age
    ← current time - runnable_at
```

Conceptually:

```text
effective_priority =
    base_priority
    + urgency
    + deadline_pressure
    + bounded_aging
```

The exact weighting remains a Scheduler policy decision.

The current effective value is not authoritative database state.


# 32. Resource Capacity Model

Resource availability is derived:

```text
available =
    capacity
    -
    SUM(active reservations)
```

Do not maintain two independent authoritative numbers such as:

```text
capacity
available_capacity
```

unless a later optimization transactionally maintains both.

Phase 1 should keep:

```text
capacity = authoritative resource limit
reservations = authoritative allocation
```

# 33. Table: reservations

## 33.1 Purpose

Record capacity reserved by admitted SchedulerWork.

## 33.2 Schema

```sql
CREATE TABLE reservations (
    reservation_id      TEXT PRIMARY KEY,

    scheduler_work_id   TEXT NOT NULL,

    resource_id         TEXT NOT NULL,

    quantity            INTEGER NOT NULL
                        CHECK (quantity > 0),

    created_at          TEXT NOT NULL,

    released_at         TEXT,

    status              TEXT NOT NULL
                        CHECK (
                            status IN (
                                'ACTIVE',
                                'RELEASED'
                            )
                        ),

    FOREIGN KEY (scheduler_work_id)
        REFERENCES scheduler_work(scheduler_work_id),

    FOREIGN KEY (resource_id)

    UNIQUE (scheduler_work_id, resource_id)
);
```

Phase 1 assumes one Reservation row per required Resource for a SchedulerWork item.

# 35. Atomic Scheduler Admission

Scheduler admission must be transactional.

Conceptually:

```text
BEGIN IMMEDIATE

1. Verify SchedulerWork is READY.
2. Verify Task concurrency policy.
3. Resolve required resources.
4. Verify all required capacity.
5. Insert Reservation rows.
6. Change SchedulerWork → ADMITTED.
7. Record DecisionRecord.

COMMIT
```

The database transaction must end before external work begins.

Never hold it over:

```text
LLM inference
network request
tool execution
process launch
sleep
```

---

# 36. Reservation Recovery

If Pinky crashes after reserving resources:

```text
Reservation = ACTIVE
```

but downstream execution was never established, startup recovery must detect and reconcile the orphaned reservation.

Recovery must not permanently lose capacity.

# 41. Cross-Entity Invariants

The implementation must preserve:

```text
1. Every Occurrence references exactly one Task.

2. Every Occurrence activation references the Trigger that produced it when applicable.

3. Every SchedulerWork row references exactly one Occurrence.

4. Every Reservation references exactly one SchedulerWork and Resource.

5. Active Reservation quantity never exceeds Resource capacity.

6. Event identity is unique.

7. Event log position is unique and monotonic.

8. Event identity and Event log position are not conflated.

9. Source-level Event deduplication is durable when source identity/dedupe keys are available.

10. Reprocessing the same logical trigger cannot create a duplicate Occurrence.

11. Task lifecycle state is independent from SchedulerWork state.

12. Occurrence lifecycle state is independent from SchedulerWork state.

13. READY work is reconstructible after restart.

14. ADMITTED work is reconstructible after restart.

15. Stale Reservations are recoverable and releasable.

16. Scheduler admission cannot occur without valid concurrency/resource admission.

17. Scheduler admission does not imply execution success.

18. DISPATCHED does not imply COMPLETED.

19. Effective priority is derived rather than authoritative persisted state.

20. Consumer offsets advance only after the represented consumer operation succeeds.

21. Outbox publication never deletes Event history.

22. Important state transitions that require Event publication commit state + Event + Outbox atomically.

23. Scheduler transactions never span external execution.

24. Recovery is idempotent.

25. Historical Events remain available even after consumers process them.

26. Components do not bypass owning subsystems by issuing arbitrary state mutations.
```

---

# 42. Transaction Map

## 42.1 Event Ingestion

```text
Candidate Event
    ↓
validate / dedupe
    ↓
BEGIN
    ↓
insert events
insert outbox
    ↓
COMMIT
```

## 42.2 Event-Triggered Activation

```text
Event consumer
    ↓
BEGIN
    ↓
match task_triggers
create Occurrence(s)
create SchedulerWork
advance consumer offset
COMMIT
```

The `activation_key` uniqueness constraint makes activation replay-safe.

## 42.3 Schedule Activation

```text
timer wake
    ↓
BEGIN
    ↓
verify trigger
create Occurrence
create SchedulerWork
advance next_fire_at
advance last_fired_at
commit required Event/outbox state
COMMIT
```

This prevents:

```text
schedule advanced without occurrence
```

or:

```text
duplicate occurrence after crash
```

## 42.4 Scheduler Admission

```text
BEGIN IMMEDIATE
    ↓
verify READY
    ↓
check concurrency
    ↓
check resources
    ↓
create reservations
    ↓
ADMITTED
    ↓
DecisionRecord
    ↓
COMMIT
```

## 42.5 Cancellation Before Dispatch

```text
BEGIN
    ↓
cancel SchedulerWork
release Reservations
cancel Occurrence where required
record decision/event where required
COMMIT
```

# 43. Candidate Scheduler Query

The Run Scheduler needs work conceptually equivalent to:

```text
SchedulerWork.state = READY

AND Occurrence.status = ACTIVATED

AND Task.lifecycle_state = ACTIVE

AND Occurrence.runnable_at <= now

AND Occurrence has not passed a hard expiration/deadline
```

Candidate ordering is then determined by:

```text
effective priority
deadline pressure
bounded aging
stable tie-breakers
```

Resource/concurrency checks occur during admission.

---

# 44. Recurring Schedule Semantics

A recurring Task remains one Task.

```text
Task T1
    │
    ├── Trigger TGR1
    │      │
    │      ├── Occurrence O1
    │      ├── Occurrence O2
    │      └── Occurrence O3
    │
    └── remains ACTIVE
```

Each scheduled activation gets a deterministic `activation_key`.

The trigger stores its durable:

```text
next_fire_at
last_fired_at
```

so the Wake Scheduler can reconstruct state after restart.

---

# 45. Event-Triggered Activation Semantics

Example:

```text
FILE_CREATED
    ↓
Task Trigger TGR1 matches
    ↓
activation_key(task, trigger, event_seq)
    ↓
Occurrence
    ↓
SchedulerWork
```

If the same Event is replayed:

```text
same activation_key
    ↓
UNIQUE constraint
    ↓
no duplicate Occurrence
```

This is stronger than relying only on an in-memory "already processed" set.

---

# 46. Task Dependency Semantics

Example:

```text
Task A
    ↓
COMPLETED

Task B
    ↓
depends_on A
```

The dependency subsystem finds:

```text
task_dependencies.depends_on_task_id = A
```

and reevaluates B's eligibility.

The database does not automatically set B to READY.

Eligibility remains domain logic.

# 50. Retention and Deletion

Phase 1 prioritizes correctness.

## Events

Retain.

Future retention/archival policy can be added after replay requirements are measured.

## Tasks

Prefer:

```text
CANCELLED
COMPLETED
```

over deletion.

## Task Triggers

Disable when no longer active; retain when historical traceability is useful.

## Occurrences

Retain historical records.

## SchedulerWork

May eventually be compacted/archived after downstream completion and retention policy are established.

## Reservations

Released reservations may eventually be compacted.

## DecisionRecords

May eventually have bounded retention.

Schema changes must be versioned.

Recommended conceptual structure:

```text

    001_initial.sql
    002_event_identity.sql
    003_task_triggers.sql
    004_dependencies.sql
```

Never change an existing database schema without a recorded migration.

```text
3. outbox

4. consumer_offsets

5. tasks

6. task_triggers

7. task_dependencies

9. scheduler_work
```

# 53. Acceptance Tests

Before moving beyond Scheduler, the database/runtime combination must demonstrate:

```text
✓ Event survives process restart.

✓ Duplicate source Event is rejected/deduplicated.

✓ Outbox survives a crash before publication.

✓ Consumer replay works after a crash before offset commit.

✓ Event-triggered Task activation is idempotent.

✓ Schedule activation is idempotent.

✓ Multiple triggers can coexist on one Task.

✓ Task dependencies can be discovered in reverse.

✓ Scheduler READY work can be reconstructed after restart.

✓ Effective priority can be calculated from persisted inputs.

✓ Aging is bounded.

✓ Resource capacity cannot be over-reserved.

✓ Concurrent admissions cannot both consume the same capacity.

✓ Cancellation releases Reservations.

✓ Expired work cannot return to READY without a new activation.

✓ Scheduler decisions explain admission/defer/block reasons.

✓ No database write transaction spans external execution.
```

# 55. Final Architectural Rule

The database should faithfully represent this lifecycle:

```text
                     EVENT
                       │
                 may activate
                       ▼
                     TASK
                       │
                  trigger fires
                       ▼
                  OCCURRENCE
                       │
                   eligibility
                       ▼
                SCHEDULER WORK
                       │
               priority / fairness
                       ▼
                  ADMISSION
                       │
               resource reservation
                       ▼
                   DISPATCH
                       │
                       ▼
                 [EXECUTION]
```

The database is responsible for making the durable portions of this lifecycle recoverable and internally consistent.

It is not responsible for making the LLM, queue implementation, or future Execution engine into the source of truth.
